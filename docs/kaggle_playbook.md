# Kaggle Playbook

Этот документ — общий шаблон для Titanic, House Prices и любых следующих табличных соревнований.

## 1. Сначала формулирую задачу

| Вопрос | Что нужно понять |
|---|---|
| Что предсказывается? | Тип таргета и формат submission |
| Какая метрика? | Как именно будет оцениваться модель |
| Где возможна утечка? | Какие признаки нельзя считать на полном датасете |
| Какой тип данных? | Табличные данные, пропуски, категориальные признаки, групповые связи |

## 2. Потом выбираю бейзлайн

| Тип задачи | Бейзлайн | Почему это хороший старт |
|---|---|---|
| Titanic | Logistic Regression + простая схема препроцессинга | Быстрый, интерпретируемый, хорошо показывает качество фичей |
| House Prices | Ridge/Lasso + one-hot + заполнение чисел | Стабилен на табличных данных и хорошо объясняет feature engineering |

Бейзлайн нужен не для красоты. Он нужен, чтобы быстро ответить на три вопроса:

| Вопрос | Что отвечает бейзлайн |
|---|---|
| Пайплайн вообще работает? | Да или нет |
| Есть ли сигнал в данных? | Да или нет |
| Где копать дальше? | В фичи, модель, обработку пропусков, блендинг |

## 3. Строю проект как набор слоёв

| Слой | Ответственность | Почему это удобно |
|---|---|---|
| data | Чтение сырых файлов | I/O отдельно от логики |
| features | Feature engineering | Легко проверять и менять |
| models | Реестр моделей и preprocessing | Ясно видно, что сравнивается |
| training | CV, OOF, blending, export | Одинаковая оценка для всех кандидатов |
| run_pipeline | Одна точка запуска | Проверяющему не нужно искать вход по всему проекту |

## 4. Что обязательно сохраняю после каждого запуска

| Артефакт | Зачем он нужен |
|---|---|
| CV-таблица | Видно, какие модели стабильнее |
| OOF-предсказания | Можно проверить бленд и ошибки |
| submission CSV | Можно сразу отправить в Kaggle |
| summary JSON | Можно восстановить настройки запуска |

## 5. Как объясняю проект ревьюеру

Если коротко, я отвечаю так:

1. Сначала я понял задачу и метрику.
2. Потом собрал простой, честный бейзлайн.
3. Потом отдельно проверил, какие фичи реально помогают.
4. Потом сохранил результаты так, чтобы любой запуск можно было разобрать постфактум.

## 6. Как это переносится на новые соревнования

| Что я переиспользую | Как именно |
|---|---|
| Структуру слоёв | data / features / models / training / pipeline |
| Логику проверки | CV, OOF, report files |
| Привычку к объяснимости | Каждое решение должно иметь причину |
| Артефакты | Чтобы не терять историю экспериментов |
